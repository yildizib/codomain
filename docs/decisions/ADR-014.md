# ADR-014: Use Streamable HTTP for the hosted MCP server

Status: Accepted

Date: 2026-09-17

### Context

Codomain needs a remotely hosted Java/Spring MCP server that external AI clients
can configure without installing a local Codomain process. Spring AI supports
STDIO, legacy HTTP/SSE, Streamable HTTP, and stateless HTTP variants.

### Decision drivers

- Use the current MCP transport intended to replace legacy HTTP/SSE.
- Keep the hosted service compatible with Spring MVC and Spring Security.
- Avoid a local per-client server installation.
- Preserve asynchronous domain processing without requiring a reactive web stack.

### Considered options

- STDIO with a local Codomain process.
- Legacy HTTP/SSE.
- Streamable HTTP with Spring WebFlux.
- Streamable HTTP with Spring WebMVC.

### Decision

V1 uses Spring AI's MCP Server WebMVC starter with Streamable HTTP. The MCP
Server remains an independently deployed remote Spring Boot application. Domain
operations return accepted operation identities and expose progress through MCP;
their durability does not depend on holding an HTTP stream open.

Spring Security and Codomain's account-scoped API-key authorization protect the
MCP endpoint. The transport starter is not treated as an authentication layer.
Legacy HTTP/SSE and STDIO are not supported V1 transports. Each advertised V1
client must pass compatibility tests before its configuration is published.

### Consequences

- The MCP Server can use the servlet stack already familiar to the project.
- Dashboard instructions provide a remote Streamable HTTP endpoint and secret
  placement guidance.
- Client support is evidence-based rather than assumed from generic MCP support.
- A future local STDIO adapter can be added without changing application use
  cases if product demand justifies it.

### Revisit when

- A required client lacks reliable Streamable HTTP support.
- MCP transport recommendations or Spring AI support materially change.
- Measured concurrency requires a different transport implementation.
