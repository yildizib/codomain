# ADR-016: Use portable ClamAV scanning and mounted artifact paths

Status: Accepted

Date: 2026-09-17

### Context

V1 needs real malware scanning in local, test, and VPS deployments. Artifact
storage may be backed by an operator-managed network mount, but application code
does not need storage-protocol-specific behavior.

### Decision drivers

- Exercise the real scanner before launch.
- Keep scanner integration portable across developer and VPS environments.
- Keep storage implementation simple and compatible with ordinary mounts.
- Preserve quarantine and sealed-content isolation.

### Considered options

- Start with a mock scanner only.
- Install and invoke host-specific ClamAV commands directly.
- Integrate ClamAV behind a configurable service boundary.
- Add application-level NFS APIs and provisioning.

### Decision

V1 uses ClamAV behind a narrow scanner interface. The normal deployment runs
ClamAV as a containerized sidecar or private service with configurable connection,
timeout, and signature-freshness policy. Unit tests may use a fake implementation,
but integration and end-to-end validation use real ClamAV.

Applications read and write configured POSIX paths. Local volumes or
operator-managed mounts may back those paths. Codomain does not provision NFS or
use NFS-specific application APIs. The separate content Nginx VPS mounts sealed
content read-only and never mounts quarantine.

### Consequences

- Scanner outages, stale signatures, timeouts, and incomplete scans block preview.
- Local and VPS environments share the same scanner contract.
- Operators remain responsible for providing and securing any network mounts.
- Tests must prove path permissions and Nginx isolation with ordinary mounts.

### Revisit when

- ClamAV coverage, throughput, or signature operations do not meet requirements.
- Object storage or another artifact backend is selected.
- Deployment automation expands to manage storage infrastructure.
