# ADR-012: Use Spring Boot applications with application-owned MQ delivery

Status: Accepted

Date: 2026-09-10

### Context

Long-running file processing must survive application restarts without coupling
MCP requests to scan duration. The user selected Java / Spring Boot and requires
insert-only outboxes, source traceability and worker inbox processing without a
separate outbox relay.

### Decision drivers

- Separate browser account UI, MCP operations and background execution.
- Recover committed work and tolerate duplicate delivery.
- Keep outbox messages immutable and processing outcomes traceable.

### Considered options

- A single synchronous application.
- Producers plus a separate outbox relay service.
- Three applications with each producer delivering and recovering its own messages.

### Decision

Use three independently deployable Spring Boot monoliths: Dashboard MVC, MCP
Server and a continuous Deployment Worker. Every application writes business
intent and its outbox in one local DB transaction, commits, then sends to MQ
itself. Each application also recovers its own unconfirmed sends at startup and
periodically. No separate relay process, service or deployment is introduced.

All outboxes, including the worker result outbox, permit INSERT only. Record
send attempts, errors and broker confirms in an append-only delivery journal.
Runtime roles have no UPDATE/DELETE privilege on these tables. Ordinary domain
state and worker inbox/job state can be updated. Administrative retention is a
separate unresolved policy.

Use stable `app-name:outboxId` message identities with globally unique outbox
IDs. Record source, operation, correlation, causation, type/schema version and
safe account/key identity. Request idempotency is separate from delivery
identity. Repeated delivery uses the same message ID and payload.

Worker inbox deduplication and durable job creation commit before ACK. Shared
worker-owned PostgreSQL state, leases and idempotent steps recover interrupted
jobs. Keep outcomes and attempt errors; persist result and worker outbox together
before the worker sends the result. Result consumers deduplicate and reject stale
state updates. MQ carries metadata/references, not file bytes.

This extends ADR-009's state-machine and retry guarantees; it does not supersede
its publication concurrency or failure guarantees.

### Consequences

- Delivery is at-least-once; inbox alone does not make filesystem effects atomic.
- Producer confirmation loss may cause duplicate sends, handled by consumers.
- No external relay is needed, but every producer implements durable recovery.
- Broker, routing, backoff, poison-message policy and physical DB placement are
  unresolved. Containerized runtime is intended; Compose is recommended, not
  selected over Kubernetes yet. Exact Java/Spring versions are not selected.

### Revisit when

- Throughput, availability or operations require a different delivery topology.
- Broker semantics or multi-region processing require stronger ordering controls.
