# ADR-017: Fix the V1 runtime, messaging, migration, and identity baseline

Status: Accepted

Date: 2026-09-17

### Context

ADR-012 selected three Spring Boot applications and application-owned outbox
delivery but left exact runtime versions, broker, physical database layout and
message identities unresolved. Implementation requires one compatible,
reproducible baseline.

### Decision drivers

- Use a supported Java/Spring/MCP stack with reproducible builds.
- Keep migrations and dependencies under clear ownership.
- Run a low-overhead broker as one disk-persistent instance.
- Preserve accepted operations across application and broker restarts.
- Use simple globally unique numeric identifiers without UUIDs.
- Prevent precision loss in JavaScript-based MCP clients.

### Considered options

- Java 21 with Spring Boot 4.1.x or an older Spring Boot generation.
- Embedded broker, standalone Artemis, or RabbitMQ.
- Application-local sequences, assigned ID ranges, UUIDs, or a shared sequence.
- One identity for an operation and all of its events, or separate operation and
  event identities.
- JSON numbers or decimal strings for `BIGINT` identifiers.

### Decision

Use Java 21, Spring Boot 4.1.1, Spring Framework 7.x, Spring AI 2.0.1 and the
Gradle 9.7.1 wrapper. Spring Boot dependency management owns Spring Framework,
Liquibase and common runtime versions. The Spring AI BOM owns the MCP Java SDK.
Do not pin managed transitive dependencies independently without a later accepted
compatibility decision.

Use one PostgreSQL cluster with a shared `platform` foundation schema and
application-owned schemas protected by separate least-privilege roles. Liquibase
owns ordered migrations. Migration roles apply DDL; runtime roles receive only
required DML and shared-sequence privileges. Production role names and secret
provider remain a deployment-policy decision.

Use `platform.global_id_seq` to allocate globally unique positive `BIGINT`
identifiers. Database columns use `BIGINT`; Java uses `long`/`Long`; MCP/JSON uses
base-10 strings. Sequence values are opaque and may contain gaps. They do not
prove time ordering, ownership or authorization.

Persist instants as PostgreSQL `timestamptz` and represent them as Java `Instant`
with UTC boundary normalization. Enforce uniqueness and state-independent
invariants with database constraints, use optimistic version columns for mutable
aggregates, and use bounded database row claiming for outbox and durable-job work.

Use distinct identities:

- `operationId` identifies and correlates one business operation.
- `eventId` identifies one immutable outbox/MQ event and is the consumer inbox
  deduplication key.
- `causationEventId` optionally links a follow-up event to its source event.
- An account-scoped client `idempotencyKey`, operation type and normalized request
  fingerprint map retries to the original `operationId`.

One operation may emit multiple events, so operation and event IDs cannot be the
same identity. MQ retry preserves the same event ID and payload.

Use Apache ActiveMQ Artemis 2.42.0 as a standalone single-node broker with a
disk-backed persistent journal, durable queues/messages and explicit consumer
acknowledgement after durable inbox/job acceptance. Do not embed the broker in an
application. Every cross-application event is inserted into the producer's
insert-only outbox in the same local transaction as business intent before MQ
delivery. Each consumer enforces inbox uniqueness on `eventId` before ACK.

Artemis is transport, not the source of accepted business truth. Broker outage
leaves committed outbox events pending. V1 makes no broker HA guarantee.

### Consequences

- All services share a narrow sequence dependency but not domain-table access.
- Request idempotency and message delivery deduplication remain separate.
- Decimal-string API IDs require central boundary parsing and serialization.
- Sequence gaps are expected after rollback or caching.
- Each producer implements recovery; each consumer implements durable inbox
  deduplication.
- A single broker node is operationally simple but temporarily unavailable during
  node or disk outages.
- Version upgrades require BOM, migration, broker and compatibility validation.

### Revisit when

- Throughput or availability requires Artemis clustering or another broker.
- Separate PostgreSQL clusters make a shared sequence inappropriate.
- A future protocol requires a different public identifier representation.
- A platform upgrade changes the supported Spring Boot/Spring AI compatibility
  line.
